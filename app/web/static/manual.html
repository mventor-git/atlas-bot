Atlas HQ — Operator Manual

Two surfaces, one Atlas: Telegram (operations) + HQ Web App (management). One identity, one capability model, one domain. Humans decide; the system records.

1First launch

  1. Clone, create .env: BOT_TOKEN, SUPERADMIN_CHAT_ID (your Telegram id), DATABASE_URL empty = SQLite, SITE_ID.
  2. venv\Scripts\pip install -r requirements.txt + install LibreOffice Still (soffice on PATH).
  3. venv\Scripts\python main.py --health — config, templates, token, DB must all pass.
  4. Start the bot (host process, never a dev terminal for production). Open Telegram → /start → you are pending until approved.
  5. Web app: venv\Scripts\python -m app.web.bootstrap --username hq --chat-id <SUPERADMIN>, then run webapp.py and sign in. First screen is the setup wizard.

2The setup wizard — do this in order

1 · Start the site. Pick the active site, confirm working calendar and confirmers. 2 · Read this manual and tick “I have read the manual”. 3 · Work the checklist — every item is recomputed from your data, so it can never lie. Guidance only: the system stays fully usable throughout.

3The two surfaces

Telegram botHQ Web App
Daily field work: reports, check-in, requests, approvals on the goReview & control: HR queue, case detail, employees, grievances, DEV config, audit, health

Nothing is web-only or Telegram-only by accident: the domain services underneath are the same. Authorization is identical on both.

4Identity & access

  • Everyone starts pending. A superadmin approves → normal_user + membership on their site(s).
  • Authority = membership + capabilities + site. Roles (PM, HR, admin…) are labels that ship defaults; an explicit capability list replaces defaults, never adds.
  • Separation of duties: requester can never confirm/decide their own request; creator can never approve their own report. The service refuses even if a button is visible.
  • OWNER viewers see summaries only — never names, zones, details, or files.
  • Web logins are linked 1:1 to the same Atlas user (Telegram id). No duplicate accounts.

5Sites & active site

Site is the tenancy wall: every read default-denies cross-site, every write is stamped. Multi-site users switch the active site selector — switching never grants new authority; revoked sites simply disappear.

6Daily labor reports

Lifecycle: draft → final → approved|rejected → locked; rejected → draft (resubmit); locked → draft (admin unlock only). Finalize your draft, a reviewer approves (note required to reject), HQ/admin locks. Totals are computed, never typed. Contractor, zone, type come from the shared catalog.

7Approvals

Approve only what belongs to your active site and capability. Approval stamps who/when; rejection demands a note — the note is the clarification ask back to the creator.

8Attendance — evidence, not booleans

  • Check-in captures GPS + accuracy as evidence; verdicts (inside/outside/anomaly) derive from it. Never edit a verdict by hand — confirm, dispute, or mark exception with a note.
  • Assisted check-in names the real worker and the reason; it never auto-confirms — a confirmer owns the queue daily.
  • Wrong day? File a claim (correction/note); a decider approves/denies it. Claims, not edits.

9HR requests

Types: advance, transport, leave, mission, overtime. Chain: pending → PM confirm → HR decide → approved|rejected. Approving an advance requires a deduction month (YYYY-MM). Approved money becomes append-only payout/deduction events with states derived from them (paid, partially_deducted, closed…); disputes are explicit and resolved on record. Reject always carries a note.

10Grievances & discipline

Grievance: filed → under review → resolved (+ appeal by filer). Discipline: filed → under review → decided (+ appeal by subject; filer ≠ decider). A complaint is recorded, never auto-proven. No case ever deducts payroll by itself — money moves only through explicit money actions.

11Payroll

Runs consume approved records only under the active versioned policy (standard hours, OT multiplier, rounding, effective-from). Policy changes are append-only versions; past runs keep their snapshot. Corrections go through adjustments on locked runs, never silent edits. Explain any line to see its provenance.

12Documents & print

Approved HR requests render bilingual PDF letters (EN/AR) from validated templates; the validator is authoritative. Printing is a host folder queue watched by the print watcher — drop, print, archive. Templates are filled, never edited by hand.

13Notifications

Workflow notices go through a durable outbox (deduplicated, retried with backoff). Confirm who holds manage_payroll per site — exception notices fan out to them. Watch the outbox pending count on the health page.

14Backup & recovery

  1. venv\Scripts\python scripts/backup_db.py → integrity-checked snapshot, keeps newest 7.
  2. Schedule daily on the HQ box; copy off-box.
  3. Restore drill before trial: stop bot → swap DB → start → /start + one report view.

15Deliberate limits (honest, by design)

  • No warnings domain yet — discipline cases are shown labeled as such.
  • No clarification state on HR — reject-with-note is the channel.
  • Payroll policy is read-only in the web app until business sign-off.
  • Rates, rounding, overtime rules, retention windows: open business questions, defaults are current values, not policy.
  • Atlas Chat (when it lands) assists only — never a security authority.
